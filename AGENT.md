# agent.md — инструкции для AI-агентов

> Рабочее название проекта: **`EasySSH`**.

## 1. О проекте

SSH-клиент в духе Termius: общее ядро на Rust и **два равноправных независимых UI**:

- **Rust-UI**: нативное десктопное приложение без webview;
- **React-UI**: веб-приложение на React, SSH-шифрование в нём идёт в браузере (WASM).

Ни один UI не «главный» и не «дополнительный». У каждого свой код, свои тесты и свой темп релизов. Общее у них только ядро и контракт.

**Что делает продукт особенным** (держи это в голове при любом решении):
- лёгкий и мгновенный: быстрый старт, низкая задержка ввода, мало RAM;
- безопасность по умолчанию: ключи и секреты не покидают устройство пользователя;
- local-first: данные живут локально, синк опционален и зашифрован end-to-end;
- веб-версия без доверия к серверу: релей видит только шифртекст.

**Чем проект НЕ является:** не форк Termius, не обёртка над системным `ssh`, не облачный сервис, который хранит чужие ключи.

## 2. Структура репозитория

```
crates/
  core/       # SSH, SFTP, vault, sync, сессии, view-model. БЕЗ UI-зависимостей, wasm-совместим
  proto/      # контракт между core и UI: Command / Event / UiState (serde). Единый источник правды
  terminal/   # эмуляция терминала (обёртка над готовым крейтом) + модель отрисовки
  relay/      # TCP-релей для веба: пропускает шифртекст, ничего не расшифровывает
  wasm/       # wasm-bindgen обёртка над core для React-UI
apps/
  ui-rust/    # нативный Rust-UI (фреймворк: см. раздел 3)
  ui-react/   # React-UI (web)
  dev-cli/    # консольный стенд для проверки core без UI
spikes/       # одноразовые эксперименты (UI-спайк, WASM-спайк). Не продакшн-код
docs/         # архитектура, ADR, протокол релея, матрица паритета (parity.md)
```

**Правило слоёв:** `core` ничего не знает про UI-фреймворки и платформу. Всё платформенное (сокеты, файловая система, хранилище ключей) заходит в `core` через трейты. UI общаются с ядром только через контракт из `proto`. UI-проекты не импортируют друг друга.

## 3. Стек (решения по умолчанию)

| Область | Выбор | Примечание |
|---|---|---|
| SSH | `russh` | чистый Rust, реалистичен под WASM; `ssh2`/libssh2 не использовать (C, не идёт в WASM) |
| Async | `tokio` | в WASM через `wasm-bindgen-futures` |
| Терминал-эмуляция | `alacritty_terminal` или `wezterm-term` | **свой VT-парсер не писать** |
| Rust-UI: фреймворк | **НЕ ВЫБРАН** | кандидаты: Slint, iced. Решение по итогам UI-спайка (M0.5) в ADR. egui только для прототипов |
| Rust-UI: рендер терминала | wgpu | собственный виджет: атлас глифов, перерисовка только изменённых строк |
| React-UI | React + TypeScript (strict), Vite, pnpm | |
| React-UI: рендер терминала | xterm.js (WebGL) | |
| Ядро в браузере | `core` → WASM (`wasm-bindgen`) + `relay` | секреты остаются внутри WASM |
| Шифрование vault | Argon2id + XChaCha20-Poly1305 | только проверенные крейты RustCrypto |
| Ошибки | `thiserror` в библиотеках, `anyhow` в бинарях | |
| Логи | `tracing` | |

Любое отклонение от таблицы оформляй как ADR в `docs/adr/` и сначала спрашивай. **Не выбирай UI-фреймворк для Rust-UI самостоятельно**, пока нет ADR.

## 4. Команды

```bash
# Rust (ядро и общие крейты)
cargo fmt --all
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
wasm-pack build crates/wasm --target web      # core должен собираться под WASM

# Rust-UI
cargo run -p ui-rust --release

# React-UI
pnpm install
pnpm --filter ui-react dev
pnpm --filter ui-react lint
pnpm --filter ui-react typecheck
pnpm --filter ui-react test

# Релей и консольный стенд
cargo run -p relay
cargo run -p dev-cli
```

Перед тем как объявить задачу готовой, прогони форматирование, clippy и тесты. Для React-UI ещё lint и typecheck. Если что-то не запускалось, прямо скажи об этом.

## 5. Безопасность (критично)

Это продукт, которому доверяют ключи от серверов. Ошибка здесь стоит дороже, чем в любой другой части проекта.

- **Никогда** не логируй пароли, приватные ключи, passphrase, содержимое терминала, токены. Ни в `debug`, ни в тестах.
- Секреты в памяти храни в `secrecy::SecretString` / `zeroize`. Не клонируй их без необходимости.
- **Проверка host key обязательна.** Не добавляй режимов «принимать любой ключ», даже под флагом для отладки. TOFU делается только с явным подтверждением пользователя; при смене ключа хоста показывай жёсткое предупреждение.
- **Своя криптография запрещена.** Только проверенные крейты. Не придумывай форматы шифрования, не меняй параметры KDF «для скорости».
- `unsafe` допустим только с комментарием `// SAFETY:` и обоснованием, и только с явного согласия.
- Релей не расшифровывает трафик и не хранит ничего, кроме метаданных соединения, нужных для работы.
- **React-UI не получает приватные ключи в открытом виде.** Ключи и расшифрованный vault живут внутри WASM-модуля, JS работает с непрозрачными идентификаторами (handles). Никаких секретов в `localStorage`/`sessionStorage`; в IndexedDB только зашифрованные данные.
- Секреты не попадают в буфер обмена, скриншоты и логи UI без явного действия пользователя (в обоих UI).
- Не коммить секреты, тестовые приватные ключи и реальные хосты. Для тестов используй сгенерированные одноразовые ключи.
- Изменения в `crypto`, `vault`, проверке host key, аутентификации и релее помечай в описании PR как **security-sensitive** и не мерджи без ревью человека.

## 6. Производительность

Цели (ориентиры, а не догма; уточняются замерами):
- холодный старт Rust-UI: < 300 мс до интерактивного окна;
- RAM Rust-UI в простое с одной сессией: < 80 МБ;
- задержка ввода → отклик локального рендера: < 16 мс (оба UI);
- размер WASM-бандла `core` отслеживается в CI, рост без причины не допускается.

Правила:
- **Сначала замер, потом оптимизация.** Для горячих путей добавляй бенчмарки (`criterion`).
- Горячий путь (сокет → парсер → рендер): без лишних аллокаций и копирований, используй `bytes::Bytes` и переиспользуемые буферы.
- Каналы между задачами ограниченные (`mpsc::channel(N)`), чтобы был backpressure. Неограниченные очереди не использовать.
- Тяжёлый вывод (`cat hugefile`) не должен подвешивать UI: батчинг и троттлинг обновлений, перерисовка только изменённых областей.
- Скорость SSH ограничена сетью. Не обещай и не пиши в доках «самый быстрый SSH»: выигрыш в рендере, старте и ресурсах.

## 7. Ядро и два независимых UI

Чтобы два UI не разъезжались и не дублировали логику:

- **Состояние и логика живут в `core`.** Список хостов, состояния сессий, флоу разблокировки vault, подтверждение host key, прогресс SFTP: всё это модель в ядре.
- UI только отображает снимки состояния (`UiState`) и отправляет команды (`Command`). Ядро шлёт события (`Event`). Контракт описан в `proto`, это единственная точка стыковки.
- В UI-коде нет сетевых вызовов, криптографии и парсинга протоколов. Нужна новая фича: сначала расширяй контракт и ядро, потом рисуй экраны в нужном UI.
- **Контракт версионируется.** Изменения в `proto` обратно совместимы либо сопровождаются повышением версии и обновлением обоих UI (или явной пометкой в матрице паритета).
- **Матрица паритета** в `docs/parity.md`: список возможностей и статус в каждом UI (нет / в работе / готово). Любая фича, добавляемая в ядро, заносится в матрицу. UI могут отставать друг от друга, но это должно быть видно.
- UI-специфичные вещи (нативные меню, системный keychain, drag-and-drop файлов, PWA) живут в адаптерах внутри соответствующего UI и не протекают в `core`.
- Не делай «общих UI-компонентов» между Rust и React: это два независимых кодовых базиса.

## 8. Правила для Rust

- Edition 2021+, `rustfmt` по умолчанию, `clippy` без предупреждений.
- Публичное API `core` документируй (`///`), включая инварианты и ошибки.
- Никаких `unwrap()`/`expect()` в продакшн-коде, кроме случаев с доказанным инвариантом (с комментарием). В тестах можно.
- Ошибки типизированные, с контекстом. Пользовательские сообщения не должны раскрывать секреты.
- Фичи и `cfg(target_arch = "wasm32")` изолируй в тонких адаптерах, а не размазывай по коду.
- Новая зависимость: проверь размер, лицензию, поддержку и совместимость с WASM (для `core`). Обоснуй в описании PR. Не добавляй крейт ради пары функций.

## 9. Правила для Rust-UI

(Применимо к любому выбранному фреймворку.)

- **UI-поток не блокируется.** Любой I/O и тяжёлая работа идут через async-рантайм ядра, результат возвращается событием.
- Для терминала первоклассные требования: ввод с клавиатуры, IME, выделение и копирование текста, вставка, прокрутка, hi-dpi, корректные шрифты и лигатуры. Фреймворк, который этого не тянет, не подходит.
- Клавиатурная навигация везде, горячие клавиши настраиваемы.
- Доступность (screen reader, контраст) учитывай с самого начала, а не «потом».
- Терминальный виджет отделён от остального UI и зависит от фреймворка как можно меньше (рендер через wgpu-слой в `crates/terminal`).
- Кастомные виджеты и темы пиши в одном месте, не размазывай стили по экранам.

## 10. Правила для React-UI

- TypeScript `strict`, без `any` (если нужен, то `unknown` + сужение типов).
- Функциональные компоненты и хуки; логику вызова ядра выноси в хуки и адаптеры.
- К ядру обращайся только через WASM-обёртку и типы из `proto` (генерируй TS-типы, не пиши их руками).
- Тяжёлая работа (SSH, крипто) идёт в WebWorker вместе с WASM, главный поток остаётся свободным.
- Терминал: xterm.js (WebGL). Большие списки: виртуализация, мемоизация только по результатам профилирования.
- Доступность и клавиатурная навигация обязательны.

## 11. Тестирование

- Юнит-тесты для всего, что не требует сети: парсинг, vault, форматы, state-машины сессий, view-model.
- Интеграционные тесты SSH против контейнера с `openssh-server` (docker). Покрывай: пароль, ключ, keyboard-interactive, jump-хост, смену host key, обрыв соединения.
- Совместимость с серверами главная боль: при баге с конкретным сервером добавляй регрессионный тест или фикстуру.
- Property-тесты (`proptest`) для парсеров и (де)сериализации.
- Контрактные тесты `proto`: сериализация одинакова на нативной и WASM-сборке.
- Каждый UI тестируется отдельно: Rust-UI через view-model и ручной чек-лист терминала (ввод, IME, копирование, `cat` большого файла); React-UI компонентными тестами и e2e на ключевые сценарии (подключение, ошибка host key, ввод passphrase).

## 12. Работа с git

- Ветки: `feat/...`, `fix/...`, `chore/...`. Коммиты по Conventional Commits (`feat(core): ...`, `feat(ui-react): ...`, `feat(ui-rust): ...`).
- Небольшие PR, одна идея на PR. Изменения в ядре и в UI дели на отдельные PR.
- В описании PR: что сделано, почему, как проверено, затронут ли контракт, есть ли security-sensitive изменения.
- Не переписывай историю общих веток и не делай force-push без явной просьбы.

## 13. Как тебе работать (агент)

1. **Сначала прочитай** релевантный код и `docs/`, потом предлагай решение. Не выдумывай API, которых нет в проекте.
2. Если задача неоднозначна или затрагивает архитектуру, безопасность, контракт `proto` или выбор UI-фреймворка, **задай вопрос** до начала работы.
3. Для новой фичи уточни, в каком UI она нужна (оба, только Rust, только React), и обнови матрицу паритета.
4. Делай минимально достаточное изменение. Не рефакторь «заодно», не форматируй чужие файлы без причины.
5. Не расширяй скоуп: если заметил проблему вне задачи, опиши её отдельно, не чини молча.
6. Пиши тесты вместе с кодом.
7. Не добавляй зависимости, новые крейты в workspace и новые слои без согласования.
8. Код из `spikes/` не переносится в продакшн как есть и не импортируется из `crates/` и `apps/`.
9. Честно сообщай о результате: что сделано, что проверено, что не запускалось, где остались сомнения. Не утверждай, что «всё работает», если ты этого не проверил.
10. Если есть расхождение между этим файлом и прямой просьбой человека, следуй просьбе, но предупреди о риске, если он касается раздела «Безопасность».

## 14. Дорожная карта (порядок работ)

- **M0.** Workspace, CI (fmt, clippy, test, wasm-сборка `core`), структура папок, черновик контракта `proto`, `docs/parity.md`.
- **M0.5a. UI-спайк для Rust-UI (1–2 недели, `spikes/`).** Один экран (список хостов + вкладка с терминалом) на Slint и на iced. Критерии:
  - ввод, IME, выделение и копирование текста в терминале;
  - FPS и RAM при `cat` большого файла;
  - hi-dpi и качество шрифтов;
  - стоимость форм, списков и дерева файлов;
  - скорость итераций (hot reload, время сборки);
  - размер бинарника, доступность, лицензия (для Slint проверить совместимость с моделью проекта).
  Итог: ADR с выбранным фреймворком.
- **M0.5b. WASM-спайк (`spikes/`).** Доказать, что `russh` работает в WASM через простой релей: подключение, аутентификация по ключу, обмен данными. Это самый рискованный кусок для React-UI, проверяй его первым.
- **M1.** Ядро: подключение по SSH (пароль + ключ), PTY, сессии. Проверка через `dev-cli`.
- **M2 (два параллельных трека).**
  - Rust-UI: окно, терминал, вкладки, список хостов.
  - React-UI: WASM + релей, терминал, вкладки, список хостов.
- **M3.** Локальный зашифрованный vault, импорт `~/.ssh/config` (в обоих UI).
- **M4.** SFTP: список, загрузка/скачивание, возобновление, параллельные потоки.
- **M5.** Local-first синк (CRDT, E2E-шифрование), самохостинг синк-сервера.
- **Позже:** устойчивость сессий (опциональный серверный агент), шеринг сессий, runbooks, SSH-сертификаты через OIDC, WASM-плагины.

Не берись за пункты из «Позже», пока не закрыта база и не подтверждена надёжность.

## 15. Открытые вопросы

- UI-фреймворк для Rust-UI (решается в M0.5a).
- React-UI только веб или ещё и десктопная оболочка (например, Tauri)? От этого зависит, как React-UI получает доступ к ядру на десктопе: через WASM или через нативный вызов.
- Клин продукта: для индивидуалов (open-core), для команд (сертификаты, аудит, vault) или collaborative (шеринг сессий, runbooks).
- Лицензия проекта и модель монетизации.
- Нужен ли внешний аудит безопасности перед публичным релизом (по умолчанию: да).
